# Requirements review checklist

## Completeness
- [ ] **Summary**: Clear problem statement — the problem, who has it, what the MVP delivers
- [ ] **Context & Current State**: Grounded in actual repo/system facts (stack, relevant modules, integrations), not guesses
- [ ] **Goals & Non-Goals**: Both present; non-goals guard against scope creep
- [ ] **User Stories**: All user stories have IDs and attached acceptance criteria
- [ ] **Functional Requirements**: Prioritized (P0/P1/P2) with unique IDs and clear descriptions
- [ ] **Non-Functional Requirements**: Only relevant dimensions, each with a concrete MVP-realistic value (not aspirational boilerplate)
- [ ] **Constraints & Assumptions**: Limitations stated; unconfirmed assumptions marked
- [ ] **Out of Scope & Future Iterations**: Deferred capabilities listed with one-line reasons
- [ ] **Success Metrics**: Measurable outcomes specified
- [ ] **Open Questions**: Each tracked with an ID, what unblocks it, and who decides

## Quality
- [ ] Requirements are testable and verifiable
- [ ] No ambiguous language (avoid "should", "might", "could")
- [ ] Each requirement has a unique identifier
- [ ] Dependencies between requirements identified
- [ ] Edge cases and error scenarios explicit, not implied
- [ ] Plain professional language — readable by someone joining the project cold

## MVP fit
- [ ] The P0 set alone describes a shippable product
- [ ] No requirement exists only to sound thorough — everything changes what gets built
- [ ] Deferred ideas are recorded in Future Iterations, not silently dropped

## Stakeholder Alignment
- [ ] Business objectives clearly tied to requirements
- [ ] Target users and their journeys well-defined
- [ ] Acceptance criteria agreed upon
