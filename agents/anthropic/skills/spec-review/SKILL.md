# spec-review

Audit a phase document against its checklist, write a navigable review file, and return a concise go/no-go report.

## Inputs to collect

- **Phase** — one of `requirements`, `design`, `research`, `tasks`. If missing or invalid, list the valid options and ask.

## Step 1 — Load

1. Read active spec: `cat spec/.current-spec`.
2. Verify the phase file exists: `spec/<spec>/<phase>.md`. If not, tell the user the doc doesn't exist and stop.
3. Read the full document. Note its `Revision:` value if present (added by `spec-revise`); otherwise treat it as unrevised.
4. Read `spec/<spec>/README.md` for spec context and approval state.

## Step 2 — Apply the phase-specific checklist

Load the matching checklist from `references/` and evaluate the document against it:

- `requirements` → `references/requirements-checklist.md`
- `design` → `references/design-checklist.md`
- `research` → `references/research-checklist.md`
- `tasks` → `references/tasks-checklist.md`

For each checklist item, decide: passes / partial / fails / not-applicable.

## Step 3 — Write the review file

Write the full review to `spec/<spec>/reviews/<phase>-review.md`, overwriting any prior file at that path. Create the `reviews/` directory if it does not exist.

The review file is the source of truth for the developer's fix list and for the `spec-revise` skill, so it must contain every issue (not just the top 5). Use this structure exactly:

```markdown
# <Phase> review — <spec-id>

- **Verdict:** Ready | Needs Work | Major Issues
- **Reviewed:** YYYY-MM-DD
- **Phase doc:** spec/<spec>/<phase>.md
- **Phase doc revision at review:** <N, or "—" if no revision header>

## Top strengths

- <one line each, 2–3 bullets max>

## Issues

Each issue gets a stable ID (`R-01`, `R-02`, …), an unresolved checkbox, a line/section reference, and a concrete fix.

### P0 — Blockers

- [ ] **R-01** — `L142–148` — <concrete fix>
- [ ] **R-02** — `§4.2 — API design` — <concrete fix>

### P1 — Improvements

- [ ] **R-03** — `L201` — <concrete fix>

### P2 — Nits

- [ ] **R-04** — <ref> — <concrete fix>

## Next step

<one concrete instruction — the next single edit, or "Run spec-approve with phase <phase>" if Ready>

---

_Generated by `spec-review` on YYYY-MM-DD. `spec-revise` will flip resolved checkboxes here._
```

Rules for the file:

- Number issues sequentially across all severities, starting at `R-01`. IDs must remain stable so `spec-revise` can track them.
- If a severity group has no issues, omit that subsection.
- Keep each fix concrete — name the specific section, identifier, or sentence to change.
- If the verdict is `Ready`, the Issues section may be empty; still include the "Next step" line pointing at `spec-approve`.

## Step 4 — Reply to the user

Target **150–250 words**. Do NOT repeat the file. Structure:

1. **Verdict** — one line: `Ready` / `Needs Work` / `Major Issues`
2. **Top strengths** — 2–3 bullets max, one line each
3. **Top issues** — the top 5 by impact (P0 first), each as one bullet citing its `R-XX` ID and line reference
4. **Review file** — full path to `spec/<spec>/reviews/<phase>-review.md` and total issue count
5. **Next step** — `Run spec-revise with phase <phase>` if there are issues, or `Run spec-approve with phase <phase>` if Ready

## Notes

- This skill writes only the review file. Do NOT edit the phase document itself — that is `spec-revise`'s job.
- Overwriting the review file is intentional: the latest review is always the source of truth, and git history preserves prior cycles.
- A "Ready" verdict means the user can proceed to `spec-approve`. Don't say Ready unless you'd stake your reputation on the doc shipping as-is.
- Use specific line refs, not "the requirements section". The user wants to jump straight to the issue.
